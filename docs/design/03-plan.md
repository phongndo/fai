# Plan: the three layers and a builder API

The current round builds HFIR, MFIR, and LFIR as real layers, down to AArch64 assembly, behind a
builder API that a compiler can be written against. The C frontend comes after it, as the first
compiler built on top. Decisions are in [decisions.md](decisions.md) (rows Next round, First
target, C frontend, Dialects, Builder API).

```
 compiler ──builder API (Rust, C)──▶ HFIR ──proved lowerings──▶ MFIR ──passes──▶ MFIR
     ──isel──▶ LFIR (aarch64) ──regalloc──▶ .s ──system assembler and linker──▶ binary
```

## Done when

A program built through the C API, using every HFIR building block, compiles to an AArch64
binary that runs and prints what `fir run` prints for the same HFIR. The test suite checks this
on the fixtures and on random programs from the fuzzer, running the binaries under
`qemu-aarch64` on Linux and natively on macOS.

## Layers

Every op's declaration in the op table names the layers that allow it, and each module states its
layer (`layer hfir`, `layer mfir`, `layer lfir aarch64`). The verifier rejects an op outside its
layer, as the Layers decision requires. Today's core ops are in HFIR and MFIR, except `ptr.field` and
`ptr.index`, which are HFIR only.

**Dialects** are declared op groups in the op table, such as `aarch64.*` and the building blocks.
The op set stays closed and versioned: a dialect is added by declaring its ops, not registered at
run time. Opening it (unknown generic ops, the opaque tier) comes after this round.

## Builder API

- **Rust:** a builder generated from the op table. Each op is a method whose arguments are its
  operands, its immediates, and every modifier, so no UB choice can be left out (north star:
  "a builder API that requires explicit UB choices"). Regions and `cf.blocks` are built through
  scoped builders. Modules can be verified, printed, run in the interpreter, lowered, optimized,
  and compiled from the API.
- **C:** a stable C API exported from Rust (`extern "C"`, header generated by cbindgen) over the
  same builder, with opaque handles and ids. A C test program builds modules through it.

## HFIR building blocks

Each one is declared in HFIR only, has Lean semantics, and is lowered to MFIR by a lowering proved
correct in Lean (a refinement between the HFIR program and its MFIR lowering). The checks they
lower to are `cf.check.REASON %ok`, a core op (decision: Checks):

| Block | Ops | Lowered to | Status |
|---|---|---|---|
| Aggregate values | `agg.make`, `agg.extract`, `agg.insert`, `copy`; structs and arrays as values, parameters, results, region parameters; `mem.load`/`mem.store` leaf by leaf | One scalar per leaf; copies; one access per leaf at `ptr.offset.wrap` | Built; lowering tested |
| Checked arithmetic | `int.add.overflow.s` → `(result, overflowed)`, `sub`, `mul`, `.u`; trapping ops are the `.s.trap`/`.u.trap` modifiers | Extension, `.wrap` arithmetic, truncation, `int.cmp.ne` | Built; lowering proved |
| Tagged unions | `union<…>`; `union.make`, `union.tag`, `union.get.ub`/`.trap` (reason `tag`); SSA only | The tag and every variant's scalars (`poison` where not held); `int.cmp.eq` and `cf.check.tag` | Built; lowering tested |
| Slices | `slice`; `slice.make`, `slice.ptr`, `slice.len`, `slice.get.ub`/`.trap`, `slice.set.ub`/`.trap` (reason `bounds`) | Pointer and length; `int.cmp.ult` and `cf.check.bounds`; `int.mul.wrap` and `ptr.offset.inbounds` | Built; lowering tested |
| Field and element addresses | `ptr.field`, `ptr.index` (core HFIR ops) | `ptr.offset` by `int.const` offsets and exact products | Lowering proved |
| Exceptions | `cf.try { } catch %e { }`, `exn.throw` | Calls that name their handler in MFIR (the Exceptions decision); LFIR lowers to unwind tables | Next |

The lowering (`Fir.Lower`, `crates/fir/src/lower.rs`; `fir lower FILE`) scalarizes each function,
then expands it (decision: HFIR lowering). Both tools print the same lowering, and the tests run
every fixture and fuzzed HFIR program before and after lowering: the same outcome, or, where the
HFIR run is UB, the same events first. `Lower.Proof.Expand.refines` proves the expansion pass, and
so the whole lowering of functions without aggregate, union, or slice values
(`lowerFunc_refines`); the scalarizing pass is not proved yet (decision: Lowering proofs).
`fir compile` and `fir_module_compile` lower HFIR before instruction selection, and the AArch64
tests run the fixtures (`tests/blocks/` included) and fuzzed HFIR programs natively against
`fir run` of the HFIR. The builder and the C API build every block (`fir_agg_make`,
`fir_type_union`, `FIR_TYPE_SLICE`, …), and `tests/capi/modules.c` builds, runs, lowers,
optimizes, and compiles a function using each one.

## MFIR

Core ops plus the ops the target declares legal. A pass manager runs the proved rewrites (dead
stores, forwarding, copy propagation, dead code) as Rust passes, using use lists; struct field
addresses become offsets (MFIR computes offsets, per the Layout decision). Each pass is checked by
differential testing against the reference interpreter. Matching each Rust pass to its Lean proof
by construction (certificates or generated matchers) comes after this round.

**Progress:** the pass manager and the four passes are in `crates/fir/src/passes/` (decision:
Passes): `fir opt FILE [-O | --passes dse,fwd,copyprop,dce] [--remarks] [--stats]`, verifying
after every pass in development builds. Optimized fixtures and random programs (including
programs made to exercise the memory passes) refine the originals in `fir run` and still verify
(the fixtures in `fir-ref check` too). Each pass costs a few nanoseconds per op on functions of a million
ops; the whole `-O` pipeline costs less than parsing. `dse` and `fwd` match scalar stores and loads
only, as their theorems now state; `dce` deletes the building blocks that only build or take apart
values. `fir compile -O` runs the pipeline on the lowered MFIR before instruction selection.

## LFIR for AArch64

- **Dialect:** `aarch64.*` ops for the instructions fai emits, over virtual then physical
  registers, with branch-and-block control flow and a stack frame. Each op has Lean semantics,
  written by hand for this round; importing them from Arm's ASL comes in the trust round.
- **Instruction selection:** MFIR to LFIR, rule by rule, tested by differential testing.
- **Calling convention:** AAPCS64 for integers and pointers, including aggregates passed by value.
- **Register allocation:** a linear-scan or graph-coloring allocator with spilling. The Lean-proved
  certificate checker comes in the trust round.
- **Output:** GNU-syntax assembly, assembled and linked with the system toolchain (clang).

**Status.** Built (decisions: LFIR for AArch64, AArch64 semantics, Calling convention,
Instruction selection, Register allocation, Traps at run time, AOT driver, Backend testing):

- The dialect is in machine form: registers are op immediates (`Reg`), a function's code is
  `aarch64.code`. `spec/Fir/AArch64.lean` has the instructions' bits in ASL's shape;
  `spec/Fir/AArch64Machine.lean` runs LFIR over FIR's memory, and `fir-ref run` and `fir run`
  (`crates/fir/src/backend/aarch64/machine.rs`) agree on it.
- `crates/fir/src/backend/aarch64/`: `isel.rs` (all MFIR core ops, every edge-case modifier,
  integers up to 64 bits), `regalloc.rs` (linear scan with spilling, the frame, and the
  certificate check), `emit.rs` (ELF and Mach-O), `lfir.rs` (the LFIR module at either stage).
  `fir compile` drives them.
- Tests (`crates/fir/tests/aarch64.rs`): every fixture's comparable runs and random programs,
  natively under `qemu-aarch64` and in LFIR before and after allocation, with no differences;
  `FIR_FUZZ=3000` on seeds 1 and 2 included.
- HFIR compiles through its lowering (`fir::backend::prepare`), so aggregates, unions, and slices
  pass as their scalars; `cf.check` traps with reasons `bounds` and `tag` too. Integers wider
  than 64 bits compile where only their low 64 bits matter, which covers the lowering of
  `ptr.index.inbounds`, but not checked arithmetic on `i64` (checked at 65 bits) or `mul` above
  32 bits.
- Not yet: aggregates by value in the C ABI, `i128`, macOS's ABI differences (its assembly assembles, but
  isn't run), tail calls, unwind tables, and the trust-round checkers.

## Not in this round

- The C frontend (Clang AST → HFIR, decided), floats, and full varargs: the next round, the first
  compiler on top.
- Trust upgrades: Arm's ASL semantics for isel checking, the regalloc certificate checker,
  proved passes matched to their Rust implementations, the assurance report.
- Open dialects, the binary format, JIT, Wasm.

## Order

1. Layers and dialect groups; the Rust builder and C API (in parallel).
2. HFIR building blocks with their lowerings, and the MFIR pass manager; the AArch64 LFIR dialect,
   isel, regalloc, and assembly (in parallel).
3. Exceptions through all three layers; end-to-end tests through the C API.

## Progress

- **Builder API (Rust, C):** done. `lake exe gen-builder` generates the op methods and C functions;
  `ModuleBuilder` covers memory spaces, types, functions, external functions, and globals;
  `crates/fir-capi` exports it with a cbindgen header. Every verified test file and 300 fuzzer
  programs rebuild through the builder byte for byte, and `tests/capi/modules.c` builds,
  verifies, prints, and runs modules through the C API in `cargo test` (clean under ASan and
  valgrind). Building is about 2.4 times as fast as parsing (`examples/build_bench.rs`). The
  module's layer, the building blocks (union and slice types, aggregate signatures), lowering
  (`fir_module_lower`), the `-O` pipeline (`fir_module_optimize`), and compiling to AArch64
  assembly (`fir_module_compile`) are in the API too.
