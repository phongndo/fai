# Plan: the three layers and a builder API

The current round builds HFIR, MFIR, and LFIR as real layers, down to AArch64 assembly, behind a
builder API that a compiler can be written against. The C frontend comes after it, as the first
compiler built on top. Decisions are in [decisions.md](decisions.md) (rows Next round, First
target, C frontend, Dialects, Builder API).

```
 compiler ──builder API (Rust, C)──▶ HFIR ──proved lowerings──▶ MFIR ──passes──▶ MFIR
     ──isel──▶ LFIR (aarch64) ──regalloc──▶ .s ──system assembler and linker──▶ binary
```

## Done when

A program built through the C API, using every HFIR building block, compiles to an AArch64
binary that runs and prints what `fir run` prints for the same HFIR. The test suite checks this
on the fixtures and on random programs from the fuzzer, running the binaries under
`qemu-aarch64` on Linux and natively on macOS.

## Layers

Every op's declaration in the op table names the layers that allow it, and each module states its
layer (`layer hfir`, `layer mfir`, `layer lfir aarch64`). The verifier rejects an op outside its
layer, as the Layers decision requires. Today's core ops are in HFIR and MFIR.

**Dialects** are declared op groups in the op table, such as `aarch64.*` and the building blocks.
The op set stays closed and versioned: a dialect is added by declaring its ops, not registered at
run time. Opening it (unknown generic ops, the opaque tier) comes after this round.

## Builder API

- **Rust:** a builder generated from the op table. Each op is a method whose arguments are its
  operands, its immediates, and every modifier, so no UB choice can be left out (north star:
  "a builder API that requires explicit UB choices"). Regions and `cf.blocks` are built through
  scoped builders. Modules can be verified, printed, run in the interpreter, lowered, optimized,
  and compiled from the API.
- **C:** a stable C API exported from Rust (`extern "C"`, header generated by cbindgen) over the
  same builder, with opaque handles and ids. A C test program builds modules through it.

## HFIR building blocks

Each one is declared in HFIR only, has Lean semantics, and is lowered to MFIR by a lowering proved
correct in Lean (a refinement between the HFIR program and its MFIR lowering):

| Block | Ops (sketch) | Lowered to |
|---|---|---|
| Aggregate values | `agg.make`, `agg.extract`, `agg.insert`; aggregates as SSA values, parameters, results | Scalars per field, or memory for large ones |
| Checked arithmetic | `int.add.checked` → `(result, overflowed)`; language-style ops that trap with a reason | Core arithmetic with `.wrap` plus comparisons, or `.trap` |
| Tagged unions | `union.make`, `union.tag`, `union.get` (UB or trap on the wrong tag) | A tag field plus payload in memory or aggregates |
| Slices | `slice.make`, `slice.len`, `slice.get`/`slice.set` (bounds-checked, trap reason `bounds`) | Pointer, length, a check, and `ptr.index` |
| Exceptions | `cf.try { } catch %e { }`, `exn.throw` | Calls that name their handler in MFIR (the Exceptions decision); LFIR lowers to unwind tables |

## MFIR

Core ops plus the ops the target declares legal. A pass manager runs the proved rewrites (dead
stores, forwarding, copy propagation, dead code) as Rust passes, using use lists; struct field
addresses become offsets (MFIR computes offsets, per the Layout decision). Each pass is checked by
differential testing against the reference interpreter. Matching each Rust pass to its Lean proof
by construction (certificates or generated matchers) comes after this round.

## LFIR for AArch64

- **Dialect:** `aarch64.*` ops for the instructions fai emits, over virtual then physical
  registers, with branch-and-block control flow and a stack frame. Each op has Lean semantics,
  written by hand for this round; importing them from Arm's ASL comes in the trust round.
- **Instruction selection:** MFIR to LFIR, rule by rule, tested by differential testing.
- **Calling convention:** AAPCS64 for integers and pointers, including aggregates passed by value.
- **Register allocation:** a linear-scan or graph-coloring allocator with spilling. The Lean-proved
  certificate checker comes in the trust round.
- **Output:** GNU-syntax assembly, assembled and linked with the system toolchain (clang).

## Not in this round

- The C frontend (Clang AST → HFIR, decided), floats, and full varargs: the next round, the first
  compiler on top.
- Trust upgrades: Arm's ASL semantics for isel checking, the regalloc certificate checker,
  proved passes matched to their Rust implementations, the assurance report.
- Open dialects, the binary format, JIT, Wasm.

## Order

1. Layers and dialect groups; the Rust builder and C API (in parallel).
2. HFIR building blocks with their lowerings, and the MFIR pass manager; the AArch64 LFIR dialect,
   isel, regalloc, and assembly (in parallel).
3. Exceptions through all three layers; end-to-end tests through the C API.
